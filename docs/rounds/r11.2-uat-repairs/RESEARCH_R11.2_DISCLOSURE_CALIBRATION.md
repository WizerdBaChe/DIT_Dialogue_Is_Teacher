## 1　為什麼這張卡先驗尺、不先改東西

揭露句 (disclosure) 的設計就是**計數為 0 就不渲染**，所以「找不到」本身不構成缺陷證據。它有三種可能，而三者需要的處置完全不同：

1. 那份 session 真的沒有高熵字串——**不出現才是對的**；
2. 出現了，但在你沒看的位置；
3. 計數錯了，或那行根本不會渲染。

只做「應該出現卻沒出現」的單向測試，會讓一個**永遠不印那行**的實作也拿到滿分。所以本次同時做了反向對照。

樹內既有覆蓋亦已複核：`src/core/privacy/detectors.test.ts` 對三條子規則各有正負例（UUID、無前綴 commit SHA、隨機 token 為正；kebab-case、camelCase、退化重複 hex 為負），`src/core/export/transcriptRedact.test.ts` 對 Markdown 與 HTML 兩個渲染點各有「有東西可揭露就出現」與「沒東西就不出現」。

**D-006 一併驗到**：三個對照全部在高熵遮蔽規則**關閉**的狀態下執行，揭露句仍正常運作——揭露不依賴遮蔽是否啟用，這正是它存在的理由。

## 3　對 B9／B10 的裁決建議

B9 的「未通過」應改判為**無法從該次操作判定**：那份 session 的內容不可得，無法確認它屬於哪一種子情況（有分隔符／不足 20 個連續英數／熵低於 4.3 bits per char）。重測方式：任取一份含**完整 40 或 64 字元 commit hash**、UUID、或無前綴長 token 的對話即可觸發。B10 因 B9 受阻，同步重測。

（注意 D-009：`git log --oneline` 那種 7–12 字元縮寫雜湊**不會**被抓到，這是你自己裁決保留的行為，不是漏抓。）

## 4　待你裁示——那行的強調度

調查中撈到一件不屬於缺陷、但屬於你擁有的取捨。正向對照的實際輸出長這樣：

```
- 已在本機遮蔽敏感資訊：未偵測到敏感資訊
- 另偵測到 1 筆疑似高熵字串（未遮）
```

兩行同樣是無強調的項目符號，而**「未偵測到敏感資訊」排在上面**。有人 Ctrl+F 搜「遮蔽」會先撞到上一行、讀到「未偵測到」就收手，正好錯過下一行。這是文案與視覺強調的 UX 取捨，不自行更動；若要處理，可選方向：

- **A**：維持現狀（那行是給機器與細讀者看的，不需要搶注意力）。
- **B**：把兩行合併成一句，讓「已遮蔽 N 筆／另偵測到 M 筆未遮」在同一行對照出現。
- **C**：只在 `M > 0` 時給該行一個視覺強調（粗體或前綴符號），Markdown 與 HTML 同步。
